# 결정 기록

**지금 유효한 결정**과 그 근거·기각한 대안의 유일한 자리. 명세·지침은 결정을 `D-번호`로 가리키고 근거를 베껴 적지 않는다.
README 「제작 의도」의 원자료이기도 하다.

- 결정 하나 = 절 하나. 번호는 다시 쓰지 않는다.
- 뒤집히면 그 절을 고쳐 쓰고 `기각` 칸에 옛 선택을 옮긴다. 지운 결정은 번호와 함께 `철회`라고만 남긴다.
- 표지: `[요구]`(요구사항으로 정해졌다 — 바꿀 수 없다) · `[사용자]`(사용자가 정함 — 뒤집기 전에 묻는다) · `[에이전트]`(구현하며 정함).
- 쓰는 쪽은 기록 담당 에이전트(`record`)다.

---

## D-01 런타임은 Python 3.12, 패키지는 uv로만 관리한다 [에이전트]

- **근거:** 설치된 버전 중 주요 라이브러리 지원이 확실한 최신. uv가 가상환경·잠금 파일을 한 번에 관리한다.
- **기각:** Python 3.14 — 일부 라이브러리 휠 지원을 확인하지 않았다.

## D-02 대시보드는 HTML 페이지(`web/`) + 파이썬 서버(`app.py`, FastAPI)로 만든다 [사용자]

- 사용자 원문: "steamlit 말고 그냥 html 웹페이지로 구성하면 어떨거 같아? … streamlit은 사용자를 위한 웹페이지 느낌이 아닌거." 이어서 "html로 하고".
- **근거(에이전트가 비교해 제시, 사용자 수용):**
  - 서비스처럼 직접 디자인할 수 있다(사용성·시연 인상).
  - 진행 상태를 그 칸만 0.5초마다 서버에 물어 갱신한다. Streamlit은 버튼마다 전체를 다시 그려 「오늘 게시」 갱신 버그가 났었다.
  - 서버가 게시 로봇 프로세스를 띄우는 표준 구조다(D-06).
- **방식 [에이전트]:** 빌드 도구 없는 순수 HTML·CSS·JS 파일 셋(`web/`) + FastAPI. 화면 코드 안의 로직은 얇게 두고 판정은 서버 쪽 부품이 진다(D-04).
- **비용:** 화면 코드(HTML·CSS·JS)와 서버 API로 코드량이 대략 2배(정확히 재지 않음). 바꾸기 가장 싼 시점(0단계 뼈대뿐)이었다.
- **기각:** Streamlit — 사용자용 웹페이지 느낌이 아니다. 전체 재실행 구조라 진행 상태 갱신이 어색하다.
- **기각:** React 등 프레임워크 [에이전트] — 이 규모에 과하다.

## D-03 크롬은 Playwright `launch_persistent_context` + 별도 user-data-dir로 연다 [요구]

- **근거:** 크롬은 기본 프로필의 자동 제어를 막는다. 설치된 크롬(`channel="chrome"`)을 써서 브라우저를 따로 받지 않는다.
- 프로필별 구글 로그인은 사용자가 `chrome.exe --user-data-dir=…`로 **수동으로 한 번** 한다 [에이전트]. 자동화 창의 구글 로그인은 차단된다.

## D-04 판정은 화면·브라우저 코드와 분리된 함수로 둔다 — 층 구조는 두지 않는다 [사용자]

- **근거:** 허용 범위·상한·댓글 검증을 브라우저·API 없이 테스트하기 위해서다.
- **기각:** 코어/SDK 층 분리와 의존 강제 — 엔진 의존을 떼어 내려던 구조라 파이썬에는 필요 없다(사용자 지적).

## D-05 영상당 1개는 판정 함수와 DB 유니크 열 `unique_video` 둘 다로 막는다 [에이전트]

- **근거:** 판정 함수에 실수가 있어도 저장에서 거부된다. 같은 규칙을 두 번 쓰는 것이 아니라 마지막 방어선이다.
- 테스트 영상은 이 규칙의 예외다(D-17). 그런데 dev_mode(D-23)는 실행 중 설정이라 DB 인덱스 조건에 박을 수 없다. 그래서 **유니크 열 `unique_video`** 를 둔다.
- `unique_video`에는 게시 버튼을 누른 시도 중 예외(dev_mode가 켜진 상태의 테스트 영상)가 아닌 줄에만 영상 id를 채운다. 나머지 줄(버튼 전 실패·예외 줄)은 NULL.
- SQLite 유니크 인덱스는 NULL을 여러 개 허용하므로 재시도 줄(D-12)과 테스트 예외(D-17·D-23)가 부딪치지 않는다.
- **기각:** 모든 행에 거는 일반 `UNIQUE` 제약 — 테스트 영상에 두 번째 게시를 저장하지 못한다.
- **기각:** `WHERE is_test = 0` 부분 유니크 인덱스 — dev_mode를 끈 시연 때 테스트 영상의 두 번째 게시를 DB가 막지 못하고, 버튼 전 실패 뒤 재시도 줄을 DB가 거부한다.

## D-06 게시는 서버와 별도 프로세스로 돌린다 [에이전트]

- **근거:** 게시는 수십 초 걸리는 브라우저 조작이라 서버 요청과 떼어 돌린다. 진행 상태는 DB를 거쳐 서버가 읽고, 화면이 서버에 묻는다(D-02).
- (처음 근거였던 Streamlit 이벤트 루프 충돌은 D-02로 사라졌다. 결정은 유지.)

## D-07 테스트 이름은 한글 `기능_/예외_/경계_` 접두어로만 수집한다 [에이전트]

- **근거:** 정렬했을 때 성격·대상별로 뭉친다. 성격별 실행은 `-k 경계_`로 거른다.
- **비용:** 접두어를 틀리면 조용히 수집에서 빠진다 → 자동 테스트 훅이 「0개 실행」을 실패로 본다.
- **기각:** pytest 마커로 성격 구분 — 이름과 마커가 같은 정보를 두 번 갖는다.

## D-08 CLAUDE.md는 파이썬 공통 틀, 프로젝트 고유는 `docs/PROJECT.md` [사용자]

- **근거:** CLAUDE.md를 다른 파이썬 프로젝트에 그대로 가져가기 위해서다. CLAUDE.md가 PROJECT.md를 `@`로 불러온다.

## D-09 명세는 시스템 하나 = 문서 하나로 시작한다. 트리는 조건이 찼을 때 세운다 [에이전트]

- **근거:** 지금 시스템들에는 잎마다 고유 규칙을 가진 목록(설정 목록·enum)이 없다. 트리는 그 목록이 생길 때 1:1 검사 훅과 함께 세운다.

## D-10 기록은 PROGRESS · DECISIONS · tools 셋으로 두고 기록 담당 에이전트가 쓴다 [사용자]

- **근거:** 세션이 바뀌어도 같은 자리를 다시 판단하지 않게 하는 인수인계 문서다.
- 결정은 카드 여러 장이 아니라 **이 파일 하나**에 둔다 [에이전트] — 결정 수가 수십 개 수준이라 카드·목차 생성은 과하다.

## D-11 영상 불러오기는 지정 채널마다 최신 3개씩이다 (5채널 × 3 = 15개) [사용자]

- 사용자 원문: "최신영상은 3개씩만 불러오게 만들어보고".
- 값은 `config.yaml`의 `fetch.per_channel`.

## D-12 게시 실패 시 재시도한다 — 게시 버튼 전 실패에만, ③을 한 번 누를 때마다 최대 2회 [사용자]

- 사용자 원문: "실패 했을때 재시도 넣는것도 하자". 재시도 범위는 에이전트 제안을 사용자가 채택했다(D-13과 한 묶음).
- 게시 버튼 전 실패(프로필 열기·입력 실패)는 자동 재시도한다. 값은 `limits.max_retries_per_post`.
- **횟수:** ③을 한 번 누를 때마다 최대 2회 재시도(총 3번 시도). 사람이 ③을 다시 누르면 새로 센다. 사용자 원문: "재시도는 누를 때마다 최대 2회(총 3번)".
- **다시 해도 같은 실패도 재시도한다 [사용자]:** 로그인 안 됨 · 프로필 창 열림처럼 다시 해도 같은 실패라도 버튼 전 실패면 최대 2회 자동 재시도한다("재시도는 지금처럼 둔다"). 실패 이유를 가려 재시도를 줄이지 않는다. (→ D-39로 일부 바뀜: 로그인 안 됨은 설정 수준에서 먼저 막혀 크롬을 열지 않는다. 프로필 창 열림 등은 그대로. → D-56으로 다시 바뀜: 로그인 안 됨 · 프로필 창 열림 둘 다 크롬 쿠키 확인으로 게시 검사에서 먼저 막는다.)
- 게시 버튼 후 「내 댓글 확인」만 실패하면 **재시도를 막고** 화면 캡처를 보고 사람이 판단한다.
- **예외 — 사용자가 게시 중 크롬 창을 닫으면 취소다 [사용자]:** 「사용자가 크롬 창을 닫았어요」로 실패를 기록하고 자동 재시도하지 않는다. 게시 버튼 전·후 구분은 그대로 따른다.
- **근거:** 무조건 재시도하면 같은 영상에 댓글이 둘 달려 「영상당 1개」를 스스로 깬다. 무한 재시도는 상한 우회 통로가 된다.

## D-13 하루 상한은 모든 프로필 합산, 게시 버튼을 누른 시도만 센다. 「하루」는 한국 시간 자정 기준 [사용자]

- 사용자 원문: "하루 상한은 제안한 기준으로 가자". 에이전트 제안을 그대로 채택했다.
- 설정 `limits: { daily_max_comments: 10 }`이 전체 단위라 프로필별이 아니라 합산이다.
- 게시 버튼을 누른 시도는 1개로 센다. 게시 후 「내 댓글 확인」만 실패한 경우도 센다(실제로 달렸을 수 있다).
- 게시 버튼 전 실패는 세지 않는다(재시도 규칙은 D-12).
- **근거:** 상한 우회 통로(무한 재시도)를 막고, 영상당 1개를 지키기 위해서다.

## D-14 테스트 영상은 새 구글 계정 하나로 올리고, 같은 계정을 yt1 프로필에 로그인해 댓글도 단다 [사용자]

- **근거:** 자기 영상의 댓글은 검토 대기로 숨겨지지 않아 「내 댓글 확인」이 안정적이다(에이전트 제안을 사용자가 따름).
- **기각:** 메인 계정 업로드 + 새 계정 댓글 — 새 계정의 홍보성 댓글이 스팸 필터에 걸릴 수 있다.
- **기각:** 지정 채널 영상을 내려받아 재업로드 — 저작권·Content ID 위험(사용자가 제안했으나 에이전트가 반대해 기각).

## D-15 테스트 영상은 도형 슬라이드 + Windows TTS 내레이션으로 만든 51초 영상이다 [에이전트]

- 슬라이드 6장 + Windows TTS(Heami) 한국어 내레이션. 주제는 연애 고민(답장이 하루씩 늦는 썸). 직접 촬영은 하지 않았다.
- 영상 ID `z_K3rHRbqck`, 일부 공개, `config.yaml`의 `test_video_ids`에 등록. 원본 `data/test_video/test_video.mp4`는 Git 제외.
- 제목에 「테스트」를 넣지 않았다 — 제목은 댓글 초안의 재료라 초안에 「테스트」가 샐 수 있다.

## D-16 개발·시연 게시는 테스트 영상에만 한다 [에이전트]

- 사용자 이견은 없었으나 명시적으로 정한 것은 아니다.
- 지정 5채널 게시는 허용 범위 안이지만 꼭 해야 하는 것은 아니고, 시연은 직접 올린 테스트 영상에 한다.
- **근거:** 시청자인 척하는 홍보 댓글의 스팸 정책 위험을 지정 채널에 지우지 않는다.

## D-17 테스트 영상은 「영상당 1개」 규칙의 예외다. 하루 상한은 그대로 적용한다 [사용자]

- 사용자 원문: "테스트 할때는 예외로 두자." 대상은 `config.yaml`의 `test_video_ids`.
- **근거:** 개발 중 테스트 영상에 여러 번 게시해 봐야 하고, 시연 녹화 때 이미 기록이 있으면 게시가 막힌다.
- **「영상당 1개」의 뜻:** 우리 프로그램(DB 기록)이 한 영상에 다는 댓글 수다. 프로필 1~3 합산이며, 다른 시청자의 댓글은 세지 않는다.
- 하루 상한(10개, D-13)은 테스트 영상에도 그대로 적용한다 [사용자] — 사용자 원문: "테스트 영상도 하루 상한은 적용하는 게 맞아."
- DB 제약에 미치는 영향은 D-05.
- 이 예외는 `config.yaml`의 `dev_mode`가 켜져 있을 때만 적용된다 → D-23.

## D-18 화면과 부품을 나눈다 — `app.py` · `agent/` · `tests/` [사용자]

- 폴더 구조: `app.py`(서버, FastAPI — 화면이 부르는 `/api/*`. 부품을 부르기만 한다) · `web/`(화면: `index.html` · `style.css` · `app.js`) · `agent/`(models · config · store · guard · assign · trend · fetch · draft · poster · auto) · `tests/`. 부품별 책임은 `docs/system-map.md`와 `docs/systems/`가 진다(D-26).
- 사용자가 「코어랑 view를 나눌거야?」라고 물었고 에이전트가 이 구조를 제안했다. 사용자가 D-19와 함께 받아들였다.
- **근거:** 화면 코드 안의 로직은 테스트가 어렵다(D-04). 판정을 `agent/`에 두면 브라우저·API 없이 테스트한다(D-04).
- Unity 때 같은 층·어셈블리 강제는 두지 않는다(D-04).

## D-19 판정 부품은 결정론이다 — 같은 입력이면 언제나 같은 판정 [사용자]

- 사용자 원문: "개발 결과물은 랜덤가챠가 아니라 결정론적으로 가야 하쟎아. 넣어."
- **대상:** 결정론 부품 `models` · `guard` · `assign` · `trend`(D-26). `tests/test_architecture.py`의 `PURE_MODULES`에 올린다 — 지금 목록에는 `agent/guard.py`뿐이고, 나머지는 파일이 생길 때 더한다. (→ 지금은 넷 모두 목록에 올라 있고 파일도 있다 — 구조 검사가 전부 돈다.)
- **필요한 값(오늘 게시 수·현재 시각 등)은 부르는 쪽이 인자로 넘긴다.** 부품은 판단만 한다.
- **결정론이 지는 곳 [에이전트]:** AI 초안은 매번 달라질 수 있다. 결정론은 초안이 아니라 **초안을 거르는 판정**이 진다 — 어떤 초안이 나와도 게시되는 댓글은 같은 규칙을 통과한 것이다.
- **강제 [에이전트]:** `tests/test_architecture.py`가 목록의 부품에서 구문 트리로 두 가지를 검사한다. 부품 파일이 아직 없으면 이유를 남기고 건너뛴다.
  - import: 화면·브라우저·DB·네트워크·외부 API·subprocess·os·time·random 등.
  - 시각 읽기 호출: now · today · utcnow · time · monotonic · perf_counter.
- **그 테스트가 안 보는 것:** `__import__`·`importlib` 동적 불러오기, 인자로 받은 객체의 숨은 입출력 — intent 에이전트 검토 몫.
- **검증:** 일부러 random·playwright import와 `datetime.now()`를 넣은 임시 guard.py에서 두 테스트가 실패(2)했고, 규칙을 지킨 파일에서 통과(2)했다. 임시 파일은 지웠다.

## D-24 뜨기 직전 판정: 「연애」 전체 검색 · 최근 48시간 · 평균 속도로 거르고, 선택으로 최근 속도 정렬 [사용자]

- **기각:** 채널 평소 조회수 대비 — API 호출이 늘고 기준과 달라진다. 반응 비율 — 조회수가 적으면 들쭉날쭉하다.

## D-25 게시 모드는 manual / auto 둘이다 — `post_mode`로 바꾼다 [사용자]

- 사용자 원문: "제안된 댓글 초안을 사람이 검토해서 승인 되면 게시 하는 수동 모드, 승인 없이 게시 하는 자동 모드가 있으면 좋지 않을까. 이것도 토글 가능하게." 아래 정의는 에이전트 제안을 사용자가 채택했다.
- **(D-45로 뜻이 바뀜)** 처음 정의는 「초안 승인 후 게시」였으나 승인 단계가 없어져, 수동의 뜻은 「사람이 [댓글 달기]를 누름」이다. 위 사용자 원문의 「승인」은 옛 정의다.
- **manual(기본):** 초안을 읽고 사람이 [댓글 달기]를 누르면 게시한다(승인 단계 없음, D-45). 초안 칸에는 [다시 쓰기]만 있다. 기본 흐름이다.
- **auto:** 목록에서 체크한 여러 영상을 초안 → 문지기 → 게시까지 사람이 누르지 않고 프로그램이 차례로. 영상 사이 `auto.gap_seconds`, 하루 상한에서 멈춘다. 추가 기능이다.
- **근거:** 자동 모드는 자동화 운영을 보여 준다.
- **비용:** 대기열·간격·중간 실패 처리가 늘고, 사람 검토가 없어 문지기가 유일한 안전장치가 된다.

## D-27 0단계 화면 뼈대는 대시보드 명세 없이 먼저 만들었다 — 명세는 4단계에 쓴다 [에이전트]

## D-28 AI 키가 없으면 초안 자리에 「AI API 키가 설정되지 않았어요」를 강조해 보이고 다시 쓰기·게시를 막는다 [사용자]

- **기각:** 저장된 초안을 보여 주고 머리에 「AI 키 없음」만 표시 [에이전트] — 처음 안이었으나 사용자가 뒤집었다.
- **기각:** `samples/drafts.json` 같은 예시 초안 파일을 저장소에 싣기 [에이전트 제안] — 사용자가 없애라고 했다.

## D-29 1단계 구현에서 정한 것들: 시각 · 기록장 · 게시 자리 선점 · 글 조각 · 설정 읽기 [에이전트]

- 사용자가 따로 정한 것이 아니라 착수 브리핑과 구현 중 에이전트가 정했다. 사용자가 확인한 것은 명세 4개(`docs/systems/models·config·store·guard`)다.
- **한국 시간은 고정 UTC+9.** 이 PC에 시간대 데이터베이스(tzdata)가 없어 `ZoneInfo("Asia/Seoul")`이 실패한다. 한국은 서머타임이 없어 충분하다.
- **기록장은 시간대 없는 시각을 거부하고 UTC 고정 자릿수 문자열로 저장한다.** 문자열 비교가 곧 시각 비교가 된다.
- **기록장은 예외 표시를 테스트 영상 id에만 허용한다**(`Store(db_path, test_ids)`). 판정이 실수해도 DB가 막는다(D-05 취지).
- **게시 로봇은 실제 버튼을 누르기 직전에 상태를 SUBMITTED로 바꿔 DB 자리를 먼저 잡는다.** `DuplicatePostError`면 누르지 않고 REJECTED로 기록한다(`store.md`).
- **재료와의 겹침·유사도는 한글 세 글자 조각으로 센다.**
  - 두 글자 조각은 「연애·진짜」처럼 늘 있는 말로 채워져 기각.
  - 브랜드·브랜드 소개 조각은 빼고 센다.
  - 인기 댓글은 재료에서 뺀다(「영상 속」 장면을 말해야 하므로).
- **「영상마다 다르게」 비교 대상에서 같은 영상의 이전 글은 뺀다**(테스트 영상 재게시 흐름). 규칙 검사 불합격 초안도 뺀다(D-47).
- **설정(config):** 코드에 기본값을 두지 않고 빠진 키는 오류다.
  - 금지 표현 빈 목록 · 겹침 0은 오류 — 금지 조항이 조용히 꺼지지 않게.
  - 비밀 값은 `repr`에서 가린다.
  - 설정을 언제 다시 읽을지(요청마다 다시 읽기 안 포함)는 4단계 서버 명세에서 정한다. 1단계 범위 밖이라 보류. (→ D-36: 요청마다 다시 읽는다.)

## D-32 2단계 `draft`에서 정한 것들 [에이전트]

- **작가:** 한 호출 구조화 출력 JSON `{worry, comment}`. 필드 순서로 「고민 먼저」를 강제한다.
- **다시 쓰기:** 대화를 이어 붙이지 않고 「이전 초안 + 떨어진 이유」를 재료에 붙여 새로 부른다(요청이 단순하고 생각 블록을 되돌려 보낼 일이 없다). 호출 수 = 1 + `max_rewrites`.
- **끝내 불합격한 초안:** `Draft.issues`에 이유를 담아 저장한다. (처음엔 기록장이 그 초안의 승인을 거부했으나 승인이 없어져 D-45에서 게시 검사 `check_draft`가 막는다.) 게시 로봇 `preflight`(3단계)는 재료 없이 볼 수 있는 댓글 규칙(글자 수·링크·해시태그·브랜드·지어낸 후기)을 다시 본다.
- **`Draft.version`** = 몇 번째 초안(사용자가 다시 쓰기를 누른 횟수 + 1). 「고민 한 줄」은 검사하지 않는다.
- **config 새 키:** `llm.effort`(low~max 검증) · `fetch.timeout_seconds`(> 0). 코드 기본값은 없다(D-29).

## D-33 실행은 원클릭이다 — 실행 파일(당시 `시작.bat`, 지금은 `run_dashboard.bat` — D-71) 더블클릭 한 번, 터미널 배제, exe 패키징 없음 [사용자]

- **기각:** 서버 창 숨김 + 대시보드 종료 버튼 — 브라우저만 닫으면 서버가 뒤에 남고 종료 기능을 따로 만들어야 한다.

## D-34 지정 채널 영상에는 아직 절대 댓글을 달지 않는다 [사용자]

- 대상: 지정 채널의 영상(채널 단위).
- D-16(개발·시연 게시는 테스트 영상에만)을 사용자가 다시 못 박은 것이다. 지정 채널 영상은 초안도 게시 경로로 보내지 않는다.
- **강제 방법 [사용자]:** `config.yaml`의 `channel_posting` 스위치(지금 `false`). 꺼져 있으면 지정 채널 영상은 전부 게시 금지이고 테스트 영상만 게시된다. 명세는 `docs/systems/poster.md`.
  - `dev_mode`(D-23)와 따로 돈다 — 시연 때 `dev_mode`를 꺼도 풀리지 않는다.
  - 판정은 `guard.check_target(…, channel_posting)` 한 곳이고, 서버(③ 누를 때)와 게시 로봇(`preflight`)이 같은 검사(`poster.check_post`, D-36)로 부른다.
- **기각:** 「AI 게시 명령 승인 훅」 [사용자] — 명령 문자열로는 새는 곳이 많아 효과가 작다.
- **지정 채널의 특정 영상을 코드로 막지는 않는다 [사용자]** — 사용자 「그냥 둬」. 막는 것은 지정 채널 게시 스위치(위)뿐이고, 스위치를 켜면 지정 채널의 어떤 영상도 게시 대상이 된다. 「지정 채널의 영상」은 채널 단위다(설정에는 채널 ID만 둔다).
- **기각:** `dev_mode`가 켜진 동안만 테스트 영상으로 제한 [에이전트 제안] — 시연 때 `dev_mode`를 끄면 풀린다.
- `docs/PROJECT.md` 「운영 규칙」 허용 범위 아래에 채널 게시 스위치 · 뜨기 직전 게시 금지(D-22) · `dev_mode` 예외(D-23·D-35) 항목이 반영됨 [사용자 지시].

## D-35 3단계 `poster`에서 정한 것들 [사용자·에이전트]

- 명세는 `docs/systems/poster.md`. 사용자가 명세를 확인했다. 아래 중 [사용자]만 사용자가 직접 고른 것이고 나머지는 에이전트가 정했다.
- **새 댓글은 보였는데 댓글 링크(`lc`)를 못 얻으면 영상 링크로 대신 남기고 「게시 완료」로 본다 [사용자].**
- **시도는 대기(QUEUED)로 만들고, 로봇이 `store.claim`으로 원자적으로 잡는다.** 같은 시도를 두 번 띄워도 남의 줄을 덮지 않는다. 끝난 상태(완료 · 실패 둘 · 거부)는 다시 바꾸지 않는다.
- **한 번에 하나만:** `data/poster.lock` OS 파일 잠금. 잠금을 잡은 뒤에도 진행 중으로 남은 다른 줄은 「프로그램이 중간에 멈췄어요」로 정리한다(`submitted_at`이 있으면 버튼 후 실패).
- **버튼 경계 = 버튼 직전 `SUBMITTED` 기록**(영상당 1개 자리를 먼저 잡는다, D-29). 그 뒤 실패는 클릭 오류까지 전부 버튼 후 실패로 본다.
- **재시도 줄은 `root_id`로 첫 시도에 묶인다.** 화면은 첫 시도 id로 `latest_in_root`를 물어 최신 줄을 본다.
- **`preflight`는 모드와 무관하게 「저장된 합격 초안 그대로인가」(`guard.check_draft`)를 본다** — 자동 모드나 직접 실행으로 불합격 초안이 새지 않게. 재료 없는 댓글 규칙은 `guard.check_text`(`check_comment`에서 떼어 냄)로 다시 본다. (D-32의 「재료 없이 보는 규칙 재검사」를 이것으로 구체화.)
- **`preflight`는 시도 줄의 예외 표시를 믿지 않고 지금 `dev_mode`로 다시 본다**(`guard.check_exempt`) — `dev_mode`를 켜고 만든 줄을 끈 뒤 띄워도 예외가 되지 않는다.
- **댓글 확인 = 「게시 전에 없던 `lc`를 가진 같은 글 댓글」.** 테스트 영상에 같은 글이 이미 있어도 거짓 완료가 되지 않는다. 댓글 목록이 보일 때까지 최대 5초 기다린 뒤 기존 댓글을 적어 둔다.

## D-36 4단계 화면·서버 연결에서 정한 것들 [사용자·에이전트]

- 명세는 `docs/systems/dashboard.md` · `launcher.md`. 아래 [사용자]만 사용자가 직접 정한 것이고 나머지는 에이전트가 정했다.
- **[댓글 달기]를 누르면 서버도 게시 로봇과 같은 검사 함수(`poster.check_post`)로 먼저 본다 [사용자].** 걸리면 크롬을 열지 않고 그 시도를 「게시 전 검사 거부」 + 이유로 기록한다. 시연에서 「영상당 1개」가 막히는 장면이 화면과 기록에 남는다. D-34·`poster` 명세의 「서버와 로봇 두 곳」과 같은 방향이다.
- **게시 대상이 아닌 영상(채널 게시 꺼짐 · 뜨기 직전)은 [댓글 달기] 버튼을 끄고 이유를 보여 준다 [사용자].** 「이미 단 영상」 · 「오늘 상한」은 버튼을 켜 두고, 누르면 거부가 기록된다.
- **서버 창을 닫아도 하던 게시 한 건은 게시 로봇이 끝까지 마친다 [사용자].** 로봇은 창 없이 서버와 따로 뜬다. 연결이 끊기면 화면은 진행 확인을 멈추고 한 번만 알린다.
- **서버 구성 [에이전트]:** 서버 부품을 `Services`로 묶어 주입한다(테스트는 가짜로 바꾼다). 요청마다 `config`·`.env`를 다시 읽는다(D-29에서 보류한 「다시 읽을 때」의 답). 마지막 불러오기 목록은 서버 메모리에 둔다. 서버는 127.0.0.1에만 열고, `/shots`는 파일 이름만 받는다.
- **초안 [에이전트]:** 저장된 초안이 있으면 다시 쓰지 않고, 없으면 영상을 고를 때 그 자리에서 만든다(스위치가 켜져 있을 때 — 꺼져 있으면 [초안 쓰기]를 누를 때, D-46).
- **대기(`QUEUED`) 줄 정리 셋 [에이전트]:** 로봇 띄우기 실패 → 즉시 실패 / 진행을 물을 때 로봇이 잡기 전에 죽었으면 실패 / 서버 시작 때 남은 대기 줄은 취소(`store.fail_queued`). (PROGRESS가 물었던 「`QUEUED`로 영원히 남는 줄」의 답.)
- **「끝났나」 [에이전트]:** 가장 최근 줄이 끝난 상태일 때. 단 버튼 전 실패이고 로봇이 살아 있으면 끝나지 않은 것(재시도 줄이 곧 생긴다).
- **기각:** 게시 검사를 로봇에만 맡기고 서버는 곧바로 로봇을 띄우기 [에이전트] — 막히는 장면이 크롬을 열었다 닫는 실패로만 남는다.

## D-38 링크 직접 입력의 구현 방식 [에이전트]

- 명세는 `docs/systems/guard.md` · `fetch.md` · `dashboard.md`에 반영됨.
- **`guard.parse_video_id`:** 받아들이는 형태는 `youtu.be/…` · `watch?v=` · `shorts` · `live` · `embed`, 호스트는 `m.` · `www.` · `music.` 허용, 11자 id만 단독으로도 허용, 앞뒤 공백 허용. 영상 id는 ASCII 영문·숫자·`-`·`_` 11자(한글 등은 막는다). 채널 주소 · 재생목록 · 다른 사이트는 `None`.
- **`fetch.videos_by_id(ids, source)`:** 테스트 영상과 같은 길 — 키가 있으면 `videos.list`, 없으면 oEmbed. oEmbed는 채널 id를 비우므로(D-31) **키 없는 링크는 게시 대상이 아니고 초안만 된다.** `test_videos`는 이것의 TEST 판이다.
- **서버 `POST /api/videos/link {url}`:** 테스트 영상 id면 TEST로, 아니면 LINK로 가져와 서버 메모리 목록에 더한다. 400 = 링크 아님, 404 = 못 찾음.
- **게시 대상 여부는 `check_target` 그대로:** 링크 영상도 허용 채널이어야 하고 채널 게시 스위치(D-34)가 적용된다. 링크로 넣었다고 허용 범위가 넓어지지 않는다.
- **화면:** ①에 링크 입력칸 + [추가]. 넣은 영상은 목록 맨 위 「🔗 링크로 추가」로 들어가 바로 골라진다. (→ D-50으로 바뀜: 지금은 탭 규칙이고 화면 문구의 이모지는 빠졌다.)
- **근거:** 허용 범위 우회 통로를 만들지 않고 기존 판정(`check_target`)과 가져오기 길(D-31)을 재사용한다.

## D-39 프로필 배정(`assign`) — 구글 계정은 하나(유튜브1)로 가고, 로그인 여부와 배정 방식은 설정으로 뺀다 [사용자·에이전트]

- 명세는 `docs/systems/assign.md`(신규) · `config` · `models` · `poster` · `dashboard`. 아래 [사용자]만 사용자가 직접 정한 것이고 나머지는 에이전트가 정했다.
- **구글 계정은 하나(유튜브1)로 확정 [사용자].** 새 계정을 만들려 하니 휴대폰 번호 인증이 「너무 여러 번 사용됨」으로 막혀 더 만들 수 없다.
  - 프로필 유튜브1~3 중 고르기와 영상마다 돌아가며 자동 배정은 기능을 구현·테스트하되, 계정이 하나라 실제 다른 계정 게시 시연은 하지 않는다.
- **로그인 여부는 프로그램이 알아내지 않고 설정으로 뺀다 [사용자].** config 프로필마다 `logged_in: true/false`(지금 유튜브1만 true), 배정 방식 스위치 `profile_assign: manual | rotate`(지금 manual). 프로필 고르는 칸과 자동 배정 모두 `logged_in` 프로필만 쓴다. 계정이 생기면 로그인 후 true로 바꾸면 바로 돌아가며 배정된다. → D-56으로 바뀜: `logged_in` 설정은 없어지고 로그인 여부를 프로그램이 크롬 쿠키로 확인한다. `profile_assign`은 그대로.
- **기각: 로그인 여부 자동 감지 [사용자]** — 크롬 프로필의 쿠키 파일 이름을 확인하는 방식. 로그인 정보 저장소를 들여다보는 일이라 보안상 피한다. 시도하려다 자동 권한 검사가 「자격 증명 탐색」으로 막았고, 그 방향 자체를 접었다. → D-56에서 쿠키 파일 방식을 다시 쓴다(암호화된 값은 읽지 않고 이름 · 호스트 · 만료만 본다). → D-56에서 사용자가 알고 뒤집음.
- **`assign.next_profile(후보, 기록)` [에이전트]:** 결정론(D-19). 후보 중 마지막 게시 버튼 시각(`submitted_at`)이 가장 오래된 것, 안 쓴 것이 먼저(후보 순서). 버튼을 안 누른 시도(거부 · 버튼 전 실패)는 세지 않아 실패한 프로필의 차례가 넘어가지 않는다.
- **config [에이전트]:** 프로필마다 `logged_in` 필수(코드 기본값 없음, D-29), `logged_in: true`가 하나 이상, `profile_assign`은 `manual` · `rotate` 중 하나. (→ D-56으로 바뀜: `logged_in` 필수 · 「하나 이상」 규칙은 삭제. `profile_assign` 검증은 그대로.)
- **게시 검사 [에이전트]:** `poster.check_post`는 로그인함이 꺼진 프로필을 거부한다(크롬을 열지 않음). D-12의 「로그인 안 됨은 크롬을 열고 실패」는 이제 설정 수준에서 먼저 막힌다. (→ D-56으로 바뀜: 설정이 아니라 `chrome.login_state` 결과로 거부한다.)
- **서버 [에이전트]:** (→ D-56으로 바뀜: 「로그인함」은 쿠키 확인 결과.) `/api/status`는 로그인함 프로필만 내고 `profile_assign`과 rotate면 `next_profile`을 함께 낸다. (→ D-50으로 일부 바뀜: 화면 표시용 `all_profiles`가 추가됐다. 고르는 목록 `profiles`는 여전히 로그인함만.) `/api/posts`는 rotate면 요청의 프로필을 무시하고 서버가 배정하고, manual이면 로그인함 프로필만 받는다(아니면 400, 시도를 만들지 않음).
- **화면 [에이전트]:** (→ D-50으로 일부 바뀜: 로그인 전 프로필도 흐리게 보인다. → D-58로 다시 바뀜.) manual이면 로그인함 프로필만 고르는 칸, rotate면 칸 대신 「🔄 자동 배정 — 이번엔 유튜브1」. (옛 안내 문구의 설정 파일 이름은 D-44로 화면에서 뺐다 — 안내는 크롬 창을 닫아 달라는 한 줄뿐.)
- **실행기 바로가기(D-33)는 로그인 안 된 프로필도 만든다** — 로그인하러 갈 때 쓰라고. (→ D-57로 바뀜: 바로가기를 만들지 않는다.)
- **제작 의도에 쓸 거리:** 「휴대폰 인증 제한으로 계정 1개 — 배정 기능은 구현·테스트했고 설정만 켜면 동작한다」.

## D-40 뜨기 직전 영상 찾기(`trend`)의 구현 방식 — 검색은 최신순 [에이전트]

- 방법(「연애」 전체 검색 · 최근 48시간 · 평균 속도로 기준 거르기 · 선택 「다시 측정」은 최근 속도 정렬)은 D-24 [사용자] 그대로다. 아래는 그 방법을 구현하며 에이전트가 정한 것이다.
- 명세는 `docs/systems/trend.md`(신규) · `fetch` · `dashboard`, `docs/system-map.md`.
- **`agent/trend.py`(결정론, D-19):**
  - `views_per_hour` — 올린 뒤 지난 시간이 1시간보다 짧으면 1시간으로 센다.
  - `recent_velocity` — 두 측정의 조회수 차이 ÷ 간격. 줄었으면 0, 측정 순서가 거꾸로면 `ValueError`.
  - `is_rising` — 48시간 안 · 조회수 1,000~5,000 · 시간당 150 이상, 셋 다여야 참.
- **`fetch.search_recent(키워드, 이후 시각)`:** `search.list` — 한국 · 한국어 · 영상만 · **최신순(`order=date`)** · 최대 50개, 할당량 100. YouTube 키가 없으면 `FetchError`.
  - **최신순을 고른 근거(실제로 재 봄):** 조회수 순은 50개 모두 4만 뷰 이상이라 기준에 0개 든다. 최신순은 50개 중 22개가 1,000~5,000이고 20개가 기준을 통과했다. 비교로 최근 12시간 조회수 순은 16개 통과, 12~33시간 조회수 순은 0개였다.
  - 비용: 검색 한 번이 할당량 100 단위다(하루 10,000).
- **`fetch.measure(ids, now)`:** `videos.list(snippet,statistics)` 50개씩, 할당량 1. 결과는 `Measured`(video 출처 `RISING`, views, measured_at).
- **서버:**
  - `POST /api/rising/search` — YouTube 키가 없으면 409. 기준에 드는 것만 평균 속도 큰 순으로 내고, 첫 측정을 서버 메모리에 둔다.
  - `POST /api/rising/remeasure` — config `rising.remeasure`가 켜졌을 때만. 첫 측정 뒤 `remeasure_min_gap_minutes`가 안 지났으면 409 「N분 뒤」. 최근 속도 큰 순으로 낸다.
- **게시:** 뜨기 직전 영상(출처 `RISING`)은 `check_target`이 게시를 거부한다(D-22). 목록과 [댓글 달기]에 「뜨기 직전 영상은 초안까지만」을 보인다.
- **화면:** (이모지는 D-50 이후 화면에서 빠졌다.) ①에 [🔥 뜨기 직전 영상 찾기](YouTube 키가 없으면 꺼짐). 결과는 목록 맨 위에 「🔥 뜨기 직전 · 조회수 · 시간당」 배지로 들어가고, 「검색 50개 중 n개」를 안내한다. `rising.remeasure`가 켜졌으면 [다시 측정]이 보인다.

## D-41 자동 모드(`auto`)의 구현 방식 — 정의는 D-25 그대로, 게시 경로는 ③ 버튼과 같다 [에이전트]

- 자동 모드의 정의(체크한 여러 영상을 승인 없이 초안 → 문지기 → 게시까지 차례로, 영상 사이 `auto.gap_seconds`, 하루 상한에서 멈춤)는 D-25 [사용자] 그대로다. 아래는 그 정의를 구현하며 에이전트가 정한 것이다.
- 명세는 `docs/systems/auto.md`(신규), `docs/system-map.md`.
- **`agent/auto.py`:** `AutoItem`(차례 상태: 대기 · 초안 쓰는 중 · 게시 중 · 게시 완료 · 건너뜀 · 실패 · 멈춤), `AutoJob`(멈춤 신호 · `snapshot`), `AutoDeps`(서버가 넘기는 일: `open_store` · `write_draft` · `begin_post` · `pick_profile` · `wait_post` · `wait` · `now`), `run_auto`.
- **한 영상의 차례:**
  - 멈춤 신호를 먼저 확인한다.
  - 하루 상한(`guard.check_quota`)에 닿았으면 남은 차례를 모두 「멈춤」으로 하고 전체를 멈춘다.
  - 초안은 저장된 것을 쓰고, 없으면 쓴다.
  - `begin_post`는 ③ 버튼과 **같은 게시 경로**다 — 시도 생성 → `poster.check_post` → 로봇 띄움 또는 거부.
  - 로봇이 끝날 때까지 기다린다.
  - 간격은 **실제로 로봇을 띄운 영상 뒤에만, 남은 차례가 있을 때만** 둔다.
  - 검사에 걸리면 「건너뜀」+이유(간격 없음). 초안이 실패하면 그 영상만 「실패」이고 나머지는 계속한다.
- **서버:** `app.py`에서 `begin_post` · `pick_profile` · `settle`(대기 줄 정리)을 떼어 ③과 자동 모드가 함께 쓴다(로직 파편화 방지).
  - `POST /api/auto {video_ids, profile}` — `post_mode`가 `auto`가 아니면 409, AI 키가 없으면 409, 이미 돌고 있으면 409, 체크한 영상이 없으면 400.
  - `GET /api/auto` — 차례 목록과 상태. `POST /api/auto/stop` — 멈춤 신호.
- **실행 위치:** 서버 안 백그라운드 스레드(daemon). 서버 창을 닫으면 자동 실행은 멈추고, 하던 게시 한 건은 로봇이 마친다(D-36). `Services`에 `run_background`를 주입해 테스트는 직접 돌린다.
- **화면(`post_mode: auto`일 때만):** ① 영상마다 체크칸(게시 대상인 영상만 켜짐), ③에 [체크한 영상 n개 자동으로 달기] · [멈추기] · 차례 목록(1초마다 상태 갱신).
- **근거:** 자동 모드가 따로 게시 경로를 갖지 않게 해, 수동·자동이 같은 운영 규칙 검사(D-22, D-34)를 지나가게 한다.
- **비용:** 사람 검토가 없어 문지기와 `check_post`가 유일한 안전장치다(D-25). 서버 창에 묶여 있어 창을 닫으면 남은 차례는 이어지지 않는다.

## D-42 댓글 지시문은 코드가 아니라 파일(`prompts/comment_system.md`)이고, 설정 `llm.prompt_file`이 가리킨다 [사용자·에이전트]

- 사용자 원문: "댓글 작성용 프롬프트를 설정 파일로 빼놔. 언제든 변경 가능해야 해." 아래 구현 방식은 에이전트가 정했다.
- 명세는 `docs/systems/config.md` · `draft.md` · `models.md`.
- **위치:** `prompts/comment_system.md`. config `llm.prompt_file`이 가리키며, 경로는 `config.yaml` 기준이고 필수 키다(코드 기본값 없음, D-29).
- **바로 반영:** 서버가 요청마다 설정을 다시 읽으므로(D-36) 고친 지시문은 다음 초안부터 쓰인다. 재시작이 필요 없다.
- **자리표시:** `{brand}` · `{brand_desc}` · `{min_chars}` · `{max_chars}` · `{min_count}` · `{max_count}` · `{forbidden_examples}`. 목록은 `models.PROMPT_FIELDS` 한 곳이 가진다.
- **거부:** 설정 읽기가 파일 없음 · 빈 파일 · 짝이 안 맞는 중괄호 · 모르는 자리표시를 이유와 함께 거부한다. 잘못 고친 지시문이 초안 때 조용히 깨지지 않는다.
- **코드에 남긴 것:** 재료(user) 틀과 다시 쓰기 덧붙임(`build_user`)은 지시문이 아니라 구조라 코드에 둔다.
- **근거:** 초안 품질은 지시문 문구로 갈리고, 문구는 코드를 건드리지 않고 자주 고쳐 봐야 한다. 설정의 「동작은 파일로 조절」 방향(D-20)과 같다.
- **기각:** 지시문을 `draft.py` 안 문자열로 두기 — 고칠 때마다 코드를 열어야 한다.

## D-43 댓글 지시문 내용 개선 — 예시 문장을 없애고 「세 박자」 구조로 바꾼다 [사용자·에이전트]

- 사용자 결정: 의도 대조에서 나온 「놓친 것」 중 1번(초안이 지시문 예시 문장을 베낌)부터 하자고 했다 — 원문 "놓친 것부터 하자". 프롬프트 엔지니어링으로 풀릴 것 같고 댓글 프롬프트가 굉장히 짧을 것 같다는 취지. 아래 문구 내용은 에이전트가 정했다.
- **예시 문장 한 줄을 없앴다.** 모델이 그 문장을 그대로 베꼈다(5채널 초안 중 둘과 테스트 영상). 문지기 유사도가 브랜드 낱말을 빼고 세므로 못 잡았다(D-29). 문장을 주는 대신 구조를 준다.
- **「세 박자」:** 공감 → 영상 속 장면 → 그 고민이 남긴 「사주가 답할 궁금증」으로 이어 운명원 연애 사주. 운명원이 고민과 상관없이 튀어나오던 갑작스러운 다리를 없앤다. 궁금증 예(인연인지 · 연애 시기 · 그 사람 마음 · 올해 연애 흐름)는 구조의 예이지 베낄 문장이 아니다.
- **상투적 끝맺음 금지:** 「그렇게 잘 본다던데」 · 「나도 한번 보고 싶다」 · 「한번 가볼까 싶네요」. 끝맺음은 질문 · 다짐 · 혼잣말 등 매번 다르게. (→ D-67로 지움: 금지 목록이 질문형 끝맺음 쏠림을 만들었다는 에이전트 제안을 받아들임. 「세 박자」의 고정 순서도 「순서 자유」로 바뀜.)
- **광고 말투 금지:** 최고 · 강추 · 꼭 가 보세요 같은 권유·과장, 남에게 가 보라고 권하기.
- **자동 자막 오타 바로잡기:** 자막이 자동 생성이라 잘못 들린 말이 섞인다(실제로 「3세시간」). 장면을 짚을 때 바로잡아 쓴다.
- **인기 댓글 표현 베끼지 않기:** 분위기 참고만.
- **검증(같은 영상 6개 — 테스트 영상 + 지정 채널별 최신 1개, 같은 재료):** 고치기 전·후 모두 6개가 규칙 검사를 첫 시도에 통과했다. 차이는 문지기가 못 재는 품질이다.
  - 전: 6개 중 5개가 「한번 보고 싶/가볼까 싶네요」로 끝나고, 운명원이 고민과 상관없이 나왔다.
  - 후: 고민에서 궁금증(「이 사람이랑 인연인지」 · 「올해 연애 흐름」 · 「그 사람 마음」)으로 이어져 운명원으로 넘어가고, 끝맺음이 질문 · 혼잣말로 다양해졌다.
  - 바로잡기 규칙은 비교 중 한 곳에서 본 자동 자막 오타에서 나왔다.
- **남은 아쉬움:** 일부 초안은 운명원을 「들은 말투」(소문 · 주변에서)로 꺼내지 않는다. 지시문 파일을 고쳐 조정할 수 있다(D-42).
- **제작 의도에 쓸 거리:** 「예시 한 줄이 베낌을 만든다 → 문장 대신 구조로 바꿨다」는 지시문 전후 비교.

## D-44 화면에는 설정 파일 이름·키 이름을 쓰지 않는다 — 설정 방법은 설명서(README) 몫 [사용자·에이전트]

- 사용자 결정: 의도 대조에서 나온 「놓친 것」 중 화면 용어 노출을 고치자고 했다 — 원문 "화면에 보이는 설정 파일 용어 정리하자". 근거는 사용성 — 처음 보는 사람이 설명 없이 쓸 수 있는가. 아래 방식은 에이전트가 정했다(명세는 `docs/systems/dashboard.md` 갱신).
- **원칙:** 화면(HTML · 목록의 막힌 이유 · 진행 칸 · 기록의 이유)에 설정 파일 이름(`config.yaml`)·키 이름(`logged_in` · `channel_posting` · `post_mode` · `dev_mode` · `profile_assign` · `YOUTUBE_API_KEY` 등)을 쓰지 않는다. 설정하는 방법(프로필 추가 · 키 넣기)은 설명서(README)가 진다.
- **예외:** AI 키 안내 상자(D-28)는 사용자가 직접 해야 하는 일이라 `.env`와 `ANTHROPIC_API_KEY=`를 그대로 둔다.
- **바뀐 문구:**
  - 지정 채널 게시 꺼짐 → 「지정 채널 게시가 꺼져 있어요 — 지금은 테스트 영상에만 달아요」
  - 로그인 전 프로필 → 「…은 아직 유튜브 로그인 전인 프로필이에요 — 로그인한 프로필로 달아 주세요」
  - AI 키 없음 → 「② 칸의 안내대로 키를 넣고 새로고침」
  - 로봇 못 뜸 → 「다시 눌러 보고, 계속되면 프로그램을 다시 시작」(로그 경로는 코드 주석으로)
  - YouTube 키 필요 → 「설명서의 「키 넣기」 참고」
  - 자동 모드 꺼짐 → 「지금은 수동 모드라 자동으로 달 수 없어요」
- **머리 칩:** 「채널 게시 꺼짐 — 테스트 영상만」을 「게시 대상: 테스트 영상만 / 지정 채널 + 테스트 영상」으로 바꿨다. 「개발 모드」 칩은 켜져 있을 때만 「🧪 개발 모드 켜짐」으로 보이고, 꺼지면(시연) 보이지 않는다.
- **③ 안내:** 「`config.yaml`에서 `logged_in`을 true로…」 문장을 지우고 「누르기 전에 이 프로필의 크롬 창은 닫아 주세요 — 열려 있으면 로봇이 같은 프로필을 열 수 없어요」만 둔다.
- **강제:** 테스트 `기능_화면문구_설정파일_용어가_보이지_않는다`가 화면 HTML과 목록 막힌 이유에서 용어를 검사한다(변이 검사로 빨간불 확인). D-50 때 화면 문구 대부분이 `app.js`에 있어 `app.js` 문자열까지 검사하도록 넓혔다(`app.js`에 `post_mode`를 일부러 넣어 빨간불 확인).
- **비용:** 설정 방법이 화면에서 사라져 README가 반드시 담아야 한다(PROGRESS 6단계).

## D-45 ②와 ③ 사이의 [승인] 단계를 없앤다 — 사람이 초안을 읽고 [댓글 달기]를 누르는 것이 곧 결정이다 [사용자·에이전트]

- 사용자 결정: 기본 흐름에 그대로 맞추기로 했다. 기본 흐름은 ②에서 영상을 고르면 고민 한 줄과 댓글 초안이 보이고, [댓글 달기]를 누르면 실제로 게시되는 것이다. D-25의 수동 모드 정의(「초안 승인 후 게시」)와 PROGRESS의 열린 결정(승인 단계를 기본 흐름에 어떻게 맞출지)을 이것으로 닫는다.
- **기각 [에이전트 추천]:** 그대로 두기 — 사람 검토 안전장치. 에이전트는 이쪽을 추천했으나 사용자가 기본 흐름을 택했다.
- **D-25 갱신:** 수동 모드의 뜻이 「초안 승인 후 게시」에서 「사람이 [댓글 달기]를 누름」으로 바뀌었다. 수동 = 사람이 [댓글 달기]를 누름, 자동 = 체크한 영상을 프로그램이 차례로.
- **방식 [에이전트]** (명세 `guard` · `store` · `models` · `poster` · `dashboard` · `draft`를 이 결정에 맞춰 갱신):
  - **없앤 것:** `guard.check_approval` · `store.set_approved` · `Draft.approved` · 서버 `/api/videos/{id}/approve` · `reject` · 화면의 [승인] · [거절] 버튼과 「승인됨」 표시.
  - **남긴 것:** 기록장 drafts 표의 `approved` 열은 옛 파일과 맞추려 남기고 늘 0이다.
- **안전장치는 그대로다:**
  - 불합격 초안(규칙 검사 실패)은 게시 검사 `check_draft`가 막는다. 화면은 [댓글 달기]를 끄고 「②에서 [다시 쓰기]」를 안내한다. 초안과 다른 글도 막힌다.
  - 운영 규칙(허용 범위 · 영상당 1개 · 하루 상한)은 서버 · 로봇 · DB가 그대로 강제한다(D-05 · D-36).
- **[댓글 달기]가 켜지는 조건:** AI 초안 있음 · 규칙 검사 통과 · 그 영상이 게시 대상. 안내 문구는 「초안을 확인하고 누르면 크롬이 열리고 한 글자씩 타이핑해요」.
- **근거:** 기본 흐름과 맞추기 위해서다(사용자 판단). 사람이 초안을 읽고 누르는 행동이 곧 검토다.
- **비용:** 「초안을 승인해야 게시된다」는 별도의 사람 검토 관문이 사라졌다. 그 자리는 규칙 검사(문지기 · `check_draft`)와 사람의 [댓글 달기] 누름이 대신한다.
- **D-50 화면 개편에서도 유지됐다:** 시안대로면 ②의 [다음 →]으로 ③을 연 뒤 [댓글 달기]를 눌러 클릭이 하나 늘어 이 결정과 부딪혔고, 사용자가 「클릭 안 늘리기」를 골랐다(D-50).

## D-46 초안을 영상을 고르자마자 쓸지, [초안 쓰기]를 누를 때 쓸지는 설정 스위치(`llm.draft_on_select`)로 고른다 [사용자·에이전트]

- 사용자 결정: 영상을 클릭하자마자 초안을 쓰는 것은 비용에 민감하면 문제가 될 수 있으니 둘 다 되게 설정 스위치로 둔다. 사용자 원문 요지 — 「영상을 클릭하자마자 댓글 초안을 작성하는 건 비용에 민감하다면 문제가 될 수 있어. 설정 파일로 빼서 클릭하자마자 작성하게 하던가, 클릭 후 작성 버튼을 누르면 작성하게 하는 게 어때?」. D-36의 「없으면 영상을 고를 때 그 자리에서 만든다」는 이 스위치가 켜져 있을 때의 동작이 된다.
- **기본값 [에이전트 추천, 사용자 이의 없음]:** `true`(고르자마자 작성). 근거는 기본 흐름(영상을 고르면 고민 한 줄과 초안이 보인다)이고, 직전에 그 흐름에 맞추기로 했다(D-45). 사용자가 값을 명시로 확정한 것은 아니다 — 뒤집을 땐 묻는다.
- **비용:** 초안 한 번 = Haiku 호출 1번(규칙 검사에 불합격하면 최대 3번 더). 한 번 쓴 초안은 저장돼 다시 고르면 다시 부르지 않는다. 정확한 금액은 재지 않았다.
- **방식 [에이전트]** (명세 `config` · `dashboard` 갱신):
  - **config:** `llm.draft_on_select`(참/거짓, 필수 키 — 코드 기본값 없음, D-29). `Settings.draft_on_select`. `/api/status`에도 실린다.
  - **서버:** 저장된 초안이 없고 스위치가 꺼져 있으면 초안 조회가 AI를 부르지 않고 `{ai: true, pending: true}`를 낸다. 첫 초안은 [초안 쓰기]이며 기존 다시 쓰기 API를 쓴다(초안이 없으면 1번째 초안으로 쓴다).
  - **화면:** `pending`이면 ②에 「아직 이 영상의 초안이 없어요. AI를 부를 때마다 요금이 조금 들어요.」와 [초안 쓰기]를 보이고, [댓글 달기]는 꺼지며 「②에서 [초안 쓰기]를 누르면 초안이 나와요」를 안내한다.
  - **자동 모드(D-41)는 스위치와 상관없이 초안을 쓴다** — 차례마다 초안이 필요하다.
- **근거:** 비용에 민감한 사용자는 고른 영상에만 AI를 부르고, 기본 흐름대로 쓰려는 사용자는 기본값 그대로 쓴다. 동작은 파일로 조절한다는 방향(D-20)과 같다.
- **기각 [에이전트]:** 스위치 없이 항상 고르자마자 쓰기 — 목록을 훑기만 해도 영상마다 AI 요금이 든다.
- **기각 [에이전트]:** 스위치 없이 항상 버튼을 눌러 쓰기 — 기본 흐름(②에서 고르면 초안이 보인다)과 어긋난다.
- **검증:** 새 테스트 `기능_서버_자동작성이_꺼지면_고를때_AI를_부르지_않는다`는 변이 검사에서 빨간불. 브라우저에서 스위치를 잠깐 꺼 초안 없는 영상을 고르니 [초안 쓰기] 상자와 꺼진 [댓글 달기]가 보였고, 누르니 1번째 초안이 생겼다(확인 뒤 스위치를 켜 둠).

## D-47 전체 재검토(의도 대조 + 결함 검토) 뒤 고친 것들 [에이전트]

- 계기 [사용자]: 사용자가 전체를 다시 검토해 명세와 비교해 놓친 부분 · 잘못 구현한 부분을 보라고 했다. 의도 에이전트(의도 대조)와 결함 검토 에이전트 두 갈래로 훑었다. 아래는 그 결과를 에이전트가 고친 것이다. 명세 `store` · `dashboard` · `auto` · `fetch` · `config` · `models`를 맞춰 갱신했다.
- **「영상마다 다르게」 비교 대상(D-29)에서 규칙 검사 불합격 초안을 뺀다.** 검토 에이전트가 재현한 꼬임: A 합격 → B가 A와 비슷해 불합격 → A 게시가 B 때문에 막힌다.
- **기록장:**
  - 「끝났나 확인 → 바꾸기」를 `BEGIN IMMEDIATE`로 원자적으로 한다.
  - `store.fail_stopped`를 더했다(멈춘 줄 하나를 버튼 기록 전/후 실패로). `fail_unfinished`가 이것을 쓴다.
- **서버:**
  - 로봇 프로세스가 끝났는데 줄이 안 끝났으면(시작 전이든 중간이든) 실패로 정리한다 — 화면이 「진행 중」을 영원히 묻지 않게(D-36의 대기 줄 정리를 확장).
  - 자동 실행 시작의 「돌고 있나 확인 → 등록」을 잠금으로 한 번에 한다.
  - 목록을 다시 불러오면 지난 뜨기 직전 결과도 버린다.
  - `/api/status`가 화면 안내용 기준값(글자 수 · 뜨기 직전 기준)을 보낸다. 설정 오류 띠 문구에서 파일 이름을 뺐다(D-44).
- **게시 로봇은 uv의 작업 묶음(job object) 밖으로 빼서 띄운다**(`CREATE_BREAKAWAY_FROM_JOB`, 거부되면 묶음 안에서 띄움). 서버 창을 닫으면 uv가 묶음째 끝내 로봇도 죽던 것을 막아, D-36의 사용자 결정 「하던 게시 한 건은 끝까지」를 실제로 보장한다.
- **자동 모드(D-41):** 차례 사이 오류(설정 다시 읽기 등)를 `logging.error`로 남기고 남은 차례를 「실패 — 자동 실행이 오류로 멈췄어요」로 한다.
- **수집(D-31):**
  - API 호출 오류를 응답 오류뿐 아니라 httplib2 오류 · 연결 문제(`OSError`)까지 같은 길로 다룬다(목록은 「연결 문제」 이유, 자막 · 인기 댓글은 없는 재료로 대신).
  - 자막 라이브러리를 시간 한도 세션으로 불러 무한 대기를 막는다. `requests`를 직접 의존성에 추가했다(`uv add`).
- **화면:** [댓글 달기]는 누르는 순간 꺼진다(두 번 눌러도 시도 하나). 게시 중 다른 영상을 고르면 그 결과를 새 칸에 그리지 않는다. 초안 요청 경합은 무시한다. 새로고침해도 돌고 있는 자동 실행을 다시 붙잡는다([멈추기] 유지). 목록이 바뀌면 사라진 영상의 체크를 지운다. 자동 실행 중엔 [댓글 달기]가 꺼진다. 뜨기 직전 결과와 목록이 겹치면 한 줄로 합친다. 글자 수를 코드포인트로 세고, 글자 수 기준 · 뜨기 직전 안내를 설정값에서 가져온다.
- **낡은 문장 정리:** `config.yaml`의 `post_mode` 주석(「[승인]해야」 삭제, D-45), 명세의 옛 문장 다수, 빈 `main.py` 삭제.
- **남겨 둔 것(해결됨):** `docs/PROJECT.md` 허용 범위 문장에 채널 게시 스위치(D-34) 주석이 없던 것은 사용자 지시로 PROJECT.md에 반영해 닫혔다.
- **검증:** 테스트 188 통과 · ruff 깨끗 · 정체성 앵커 이상 없음 · 새 테스트 6개 변이 검사 전부 빨간불. 실제 확인은 PROGRESS에 있다.

## D-48 시연 전 개발 중 쌓인 게시 기록은 비워 둔다 — 지금 녹화하지는 않는다 [사용자]

- 사용자 원문 요지: 「지금 녹화할 건 아니지만 일단 비워는 놔」. PROGRESS의 열린 결정 「시연 전에 개발 중 쌓인 기록장을 지울지」를 이것으로 닫는다.
- **실행한 것 [에이전트]:** 기록장을 `data/backup/agent-20261020-234234.db`로 백업한 뒤 게시 기록(attempts) 8줄을 지웠다. 초안 9개는 남겼다. 뒤이은 실제 확인(D-49)이 만든 1줄도 지워서 그때는 0줄이었다. (그 뒤 D-50 화면의 실제 게시 확인이 1줄을 더했다 — attempt 10, 완료. 녹화 전에 다시 비운다.)
- **기록장 밖은 그대로다:** 유튜브 테스트 영상에 실제로 달린 댓글은 프로그램이 지울 수 없어 사용자가 직접 지워야 한다. 당시 테스트 영상 댓글 수는 6(화면 캡처에서 확인). 그 뒤 실제 게시 1회로 하나 더 늘었다(7로 추정, 유튜브에서 직접 세지 않음).
- **근거:** 기록 맨 위와 「영상당 1개」 판정(D-05·D-23)이 시연 때 개발 중 시도에 섞이지 않게 한다. 백업이 있어 되돌릴 수 있다.

## D-49 실패 + 캡처 시연은 「타이핑 중 크롬 창 닫기」로 하고, 게시 로봇이 진행 화면을 남긴다 [사용자·에이전트]

- 사용자 결정: 실패 + 캡처 화면을 시연에서 보이는 방법으로 「타이핑 중 창 닫기」(에이전트 추천 채택). 로그인 안 된 프로필은 설정에서 먼저 막혀(D-39) 캡처가 나오는 실패를 일부러 일으킬 마땅한 방법이 없었다. PROGRESS의 같은 열린 결정을 닫는다.
- **방식 [에이전트]** (명세 `docs/systems/poster.md` 갱신됨):
  - 게시 로봇이 진행 화면을 `attempt-<id>-진행.png`로 남긴다 — 영상 화면이 뜬 뒤 · 댓글 창이 열린 뒤 · 타이핑 중 15글자마다 덮어쓴다. 타이핑을 15글자 단위로 나눠 치되 글자 사이 간격 70ms는 그대로다.
  - 사용자가 크롬 창을 닫으면 그 순간은 화면을 찍을 수 없다. 그래서 닫히기 직전의 진행 화면을 취소 실패(D-12)의 캡처로 싣는다.
- **실제 확인:** 개발 서버로 테스트 영상을 게시하고 「입력 중」 3초 뒤 로봇의 크롬 창을 닫았다(창 닫기 신호). 「실패(게시 전) — 사용자가 크롬 창을 닫았어요」와 캡처(`attempt-9-진행.png`, 댓글 칸에 반쯤 타이핑된 글)가 나왔고 댓글은 달리지 않았다.
- **비용:** 타이핑 중 15글자마다 화면을 한 장 찍는다(덮어쓰기라 파일은 하나). 정확한 시간 비용은 재지 않았다.
- **검증:** 테스트 188 통과 · ruff 깨끗. 브라우저 부분은 단위 테스트 대상이 아니라 위 실제 확인이 근거다.

## D-51 시안에 있던 정보는 서버가 주도록 값을 더한다 — 조회수 · AI가 읽은 양 · 타이핑 진행 · 먼저 단 댓글 [사용자·에이전트]

- 사용자 선택: 시안에는 있지만 서버가 주지 않던 정보를 「시안 정보 전부 서버에 추가」. 아래 방식은 에이전트가 정했다. 명세 `models` · `store` · `fetch` · `draft` · `poster` · `dashboard`에 반영됨.
- **조회수의 주인은 `VideoItem.view_count`** (RSS `media:statistics views` · `videos.list` `statistics.viewCount`). 조회수가 비공개여도 목록에서 빼지 않는다(뜨기 직전 `measure`가 건너뛰는 것과 다르다). 뜨기 직전의 `views`(그때 잰 값)는 그대로 둔다. 기록장에는 저장하지 않는다.
- **AI가 읽은 양 = `Draft.transcript_chars` · `Draft.comments_read`**, `Drafter.write` 한 곳에서 채운다(③ 버튼과 자동 모드 공통). 자막 없음 = 0, YouTube 키 없음 = `comments_read` `None`, 옛 초안은 둘 다 `None` → 화면 「예전 초안이라 기록이 없어요」.
- **타이핑 진행 = `Attempt.typed_chars`**. 기존 진행 캡처 주기(D-49)와 같은 15글자 묶음마다 `on_typed`로 알리고 `store.set_typed`로 적는다. 공백 포함 코드포인트 수. 상태는 바꾸지 않고 끝난 줄은 건드리지 않는다. 화면은 「86자 중 38자」.
- **먼저 단 댓글(`previous`)**: `/api/posts/{id}`가 거부 줄일 때만, 그 영상의 영상당 1개 열(`unique_video`)이 채워진 줄(`store.posted_attempt`)에서만 찾는다 → `dev_mode` 예외 줄은 나오지 않는다(D-23). 버튼 후 확인 실패 줄이면 댓글 링크가 없을 수 있어 링크 없이도 그린다.
- **기록장 열 추가:** 열 때 없는 열(`attempts.typed_chars` · `drafts.transcript_chars` · `drafts.comments_read`)만 `ALTER TABLE ADD COLUMN`. 서버와 로봇이 동시에 열어 나는 「duplicate column」 오류만 넘긴다. 실제 `data/agent.db`에 열 3개가 붙었다(기존 초안·기록 보존, 옛 초안 9개는 읽은 양 `None`).
- **근거:** 화면은 판정하지 않고 서버가 준 값을 그린다(D-04·D-18). 값의 주인을 한 곳에 둔다.
- **비용:** 기록장 열 3개 · 서버 JSON 필드 증가. 타이핑 진행은 15글자마다 기록장에 한 번 쓴다(시간 비용은 재지 않았다).

## D-52 ③ 결과 갈래는 `PostStatus.tone` 한 곳이 정하고, 실패 문구는 버튼 전/후로 가른다 [에이전트]

- 사용자가 따로 정한 것이 아니라 B안 구현 중 에이전트가 정했다. 명세 `models` · `dashboard`.
- **갈래:** CONFIRMED = done, FAILED_BEFORE_SUBMIT · FAILED_AFTER_SUBMIT = fix, REJECTED = blocked, 나머지 progress. ③ 칸과 기록 표가 이 값으로 색을 고르고 화면은 상태를 다시 나누지 않는다(「화면은 판정하지 않는다」).
- **버튼 후 확인 실패 문구:** 「게시 버튼은 눌렀어요 — 유튜브에서 달렸는지 확인해 주세요 · 오늘 상한에 셌어요」, [다시 달아 보기]는 보이지 않는다(실제로 달렸을 수 있고 다시 눌러도 영상당 1개로 거부된다, D-12·D-13). 버튼 전 실패는 「댓글은 달리지 않았어요 · 오늘 상한에 세지 않아요」 + [다시 달아 보기].
- **손봐야 화면의 「여기서 멈춤」 칸:** 버튼 후 실패는 「확인」, 버튼 전 실패는 친 글자가 있으면 「입력」, 없으면 「열기」. 화면 표시용 추정이다.

## D-54 채널 RSS가 실패하면 한 번 더 읽고, 그래도 안 되고 YouTube 키가 있으면 API로 대신한다 [사용자·에이전트]

- 사용자 선택: RSS 실패 시 YouTube API로 대신 가져올지(키 필요 · 할당량 사용) 물었고 「응」. 아래 방식은 에이전트가 정했다. 명세 `docs/systems/fetch.md` 「목록」 절과 정체성 절.
- **계기:** 실제 채널로 돌렸을 때 5개 중 4개 RSS가 실패했다(404·500). 같은 채널도 200과 실패를 오락가락한다. 원인은 유튜브 쪽으로 보이나 확인 못 했다.
- **방식 [에이전트]** (`agent/fetch.py`):
  - `_channel_rss` — 읽기 실패면 한 번 더 읽는다.
  - 그래도 실패하고 키가 있으면 `_channel_uploads` — 채널 업로드 재생목록(채널 id `UC…` → `UU…`, `_uploads_playlist`)을 `playlistItems.list(part=contentDetails, maxResults=per_channel)`로 읽어 id를 얻고(`parse_playlist_items`) `videos_by_id(ids, Source.CHANNEL)`로 채운다. 채널당 할당량 2.
  - 대체 영상의 출처는 CHANNEL 그대로라 허용 범위 판정이 같다(링크로 넣었다고 범위가 넓어지지 않는 D-38과 같은 방향).
  - 대체도 실패하면 「RSS 이유 · API 대체도 실패: 이유」로 두 이유를 함께 담는다. 키가 없으면 대체하지 않는다.
- **실제 확인:** 실제 채널 5개 중 4개 RSS가 실패했지만 API로 대신해 15개, 실패 0. 대시보드에서 RSS 5개 모두 404인 상태에서도 「지정 채널 15」, 실패 없음.
- **관찰:** 리즈시절 LizTV는 최신 3개가 모두 「Live streaming of …」(라이브)다 — 피드에 있는 영상을 가리지 않는다는 D-31 [사용자] 결정대로 그대로 나온다.
- **비용:** 불러올 때마다 RSS가 실패한 채널 하나당 할당량 2(하루 10,000). 키가 없는 PC는 대체가 안 돼 RSS 실패가 그대로 실패로 보인다.
- **검증:** 테스트 4개 추가(`기능_목록_RSS가_한번_실패하면_다시_읽는다` · `기능_목록_RSS가_계속_실패하면_업로드목록으로_대신한다` · `예외_목록_대체도_실패하면_두_이유를_함께_알린다` · `기능_목록_업로드목록에서_영상id를_꺼낸다`), 구현 전 빨간불 확인. 212 통과 · ruff 깨끗.
- **기각:** 대체 없이 RSS 실패를 그대로 표시 — 시연 때 지정 채널 목록이 비어 보일 수 있다.

## D-55 마무리 순서 — 다듬기를 다 끝낸 뒤 README · 제작 의도 · 시연 영상 (셋 사이 순서는 미정) [사용자]

- 사용자 원문: 「README, 제작 의도도 할거 다 한다음에 마지막에 할거야. 시연 영상도.」 정한 것은 README · 제작 의도 · 시연 영상이 모두 다듬기를 다 끝낸 뒤 「마지막」이라는 것뿐이다. 셋 사이 순서는 정하지 않았다.

- **근거 [에이전트 추정]:** 다듬는 동안 화면·설정이 바뀌므로 설명서와 영상을 먼저 만들면 다시 만들어야 한다.
- **비용:** 마무리 핵심(README · 제작 의도 · 시연 영상)이 맨 뒤라 시간이 밀리면 가장 먼저 빠듯해진다. 미리 재지 않았다.
- (→ D-73: README와 제작 의도는 끝냈다. 시연 영상이 남았다.)

## D-56 프로필의 유튜브 로그인 여부는 프로그램이 크롬 쿠키 파일로 확인하고, 그 결과가 기준이다 — 설정의 `logged_in`은 없앤다 [사용자·에이전트]

- 사용자 결정: 확인 결과를 기준으로 삼고 설정의 `logged_in`을 없앨지(1) / 확인 결과를 설정에 자동으로 적을지(2)를 물었고 「1번으로 하자.」 로그인 표시는 화면에서 「상시로」 감시하고 싶다는 요청이 앞섰다(D-58). 명세는 `docs/systems/chrome.md`(신설) · `models` · `config` · `poster` · `dashboard`.
- **확인 방법 [에이전트] → 사용자가 알고 유지(원문: 「쿠키 방식은 알고 유지할게, 기록에 남겨줘」):** 프로필 폴더의 크롬 쿠키 파일(`Default/Network/Cookies`, 옛 `Default/Cookies`)을 SQLite 읽기 전용으로 열어, 호스트가 `youtube.com`으로 끝나는 `LOGIN_INFO` · `SID` 쿠키가 만료 전(만료 0 = 세션 쿠키도 유효)인지 본다. 값(암호화)은 읽지 않는다. `chrome.login_state(profile, now) -> LoginState`, 판정은 순수 함수 `logged_in_cookies`.
- **상태 셋(`models.LoginState`):** 로그인되어 있음 · 로그인 필요(쿠키 없음 · 폴더 또는 파일 없음) · 크롬 창 열림(쿠키 파일을 못 엶 — 그 프로필 크롬 창이 열리면 크롬이 파일을 잠근다. 이 PC에서 실측).

- **기각 [사용자]:** `config.yaml`에 설명 주석을 두는 방식(D-59) — 열어 보지 않아도 되게 하려는 것이 목적이다.

## D-63 AI 모델 이름과 생각하는 깊이는 옵션 페이지에 보이되 바꿀 수 없다 [사용자]

- 사용자 원문: 「모델명이랑 effort는 옵션에 노출은 하되, 변경할 수 없는 비활성화 상태로 두자. 변경하고 싶다면 yaml을 직접 수정해야 할 수 있도록.」 명세 `config` · `dashboard`.
- **방식 [에이전트]:** `config.LOCKED_OPTIONS`(`llm.model` · `llm.effort`) — `save_options`는 보내온 값과 상관없이 지금 파일의 값으로 둔다. 화면은 꺼진 칸 + 「설정 파일을 직접 고쳐야 바뀌어요」.
- **근거:** 사용자가 이유를 따로 밝히지 않았다. 모델과 생각 깊이는 초안 품질과 비용에 걸린 값(D-30)이라 화면에서 실수로 바꾸지 않게 한 것으로 보이나 추정이다. D-30의 값 자체는 그대로다.
- **검증:** 테스트 `기능_옵션저장_모델과_생각깊이는_바뀌지_않는다`(config), 실제 화면에서 칸이 꺼져 있음 확인.

## D-64 상태를 바꾸는 요청은 다른 사이트에서 온 것을 막는다 (Origin 검사) [에이전트]

- 사용자가 정한 것이 아니라 에이전트가 더했다. 명세 `docs/systems/dashboard.md`.
- **방식:** 상태를 바꾸는 `/api/*` 요청(POST · PUT · DELETE)에 `Origin` 머리가 있으면 `http://localhost:8501` · `http://127.0.0.1:8501`일 때만 받고 아니면 403. 머리가 없는 요청(같은 PC의 도구 · 테스트)은 받는다.
- **근거:** 다른 사이트 페이지가 사용자의 브라우저를 통해 이 PC의 대시보드로 몰래 요청을 보내는 것을 막는다(브라우저가 요청 출처를 `Origin`에 싣는다 — 코드 주석).
- **한계:** Host 머리는 검사하지 않는다(DNS 리바인딩, 낮은 위험 — 기존 위험 항목). 머리가 없는 요청은 통과하므로 같은 PC의 다른 프로그램은 막지 못한다.
- **검증:** 테스트 `예외_서버_다른_사이트에서_온_요청은_막는다` · `기능_서버_대시보드에서_온_요청은_받는다`(app).

## D-65 옵션 저장 실패 이유는 「설정경로: 설명」 꼴의 한국어로 내고, 화면이 칸 이름으로 바꿔 보인다 [에이전트]

- D-62의 남은 일(서버 문구에 `comment.min_chars` 같은 설정 경로가 그대로 보임)을 푼 것이다. 명세 `config` · `dashboard`.
- **서버(`agent/config.py`):** 이유 문구를 `설정경로: 설명(~요)` 꼴로 낸다(예: `comment.min_chars: comment.max_chars보다 작아야 해요`, 목록은 `channels[1]: …`). 지침 중괄호 오류의 파이썬 영어 문구는 내지 않는다.
- **화면(`web/options.js`의 `explain()`):** 앞 경로를 칸 이름으로(목록이면 「n번째 줄」), 설명 속 경로를 「칸 이름」으로, 목록 칸 열 이름(`name` 등)을 화면 열 이름으로 바꾼다. 빈 숫자 칸은 「비어 있어요」.
- **검증:** 테스트 `기능_설정읽기_이유는_설정경로로_시작한다`(config).

## D-66 개발 모드는 설정 파일로만 켠다 — 켜져 있을 때만 화면에 알리고, 오늘 게시 수 [초기화]를 쓸 수 있다 [사용자·에이전트]

- 사용자 원문: 「개발모드가 켜져 있으면 수동으로 초기화 가능했으면 좋겠는데. 개발 모드는 옵션이 아니라 yaml로만 켤 수 있게 하고. 개발 모드가 켜져 있으면 지금처럼 페이지에 개발 모드가 켜져 있다고 노출하고, 안 켜져 있으면 노출 안되게」. D-23(`dev_mode`로 테스트 영상 예외를 켜고 끈다)은 그대로다. 명세 `config` · `dashboard` · `store` · `guard`.
- **옵션 페이지에서 칸을 뺀다 [사용자]:** `config.LOCKED_OPTIONS`에 `dev_mode`를 넣어 옵션 저장으로는 바뀌지 않는다(D-63과 같은 장치).
- **칩 [사용자]:** 켜져 있을 때만 「개발 모드」 표시(D-44의 칩 규칙과 같다).
- **오늘 게시 수 [초기화] [사용자 요구, 방식은 에이전트]:** 개발 모드일 때만 머리 「오늘 남은 댓글」 옆에 버튼(확인 창). `POST /api/quota/reset`은 개발 모드가 아니면 409.
- **방식 [에이전트]:** 게시 기록은 지우지 않고 `quota_resets` 표에 초기화 시각만 남긴다(`store.reset_quota` · `last_quota_reset`). `guard.quota_window(now, reset_at)`가 「오늘 00:00(한국)과 마지막 초기화 중 늦은 때」부터 센다. 서버 머리 · 게시 로봇 재검사 · 자동 모드가 모두 이 구간으로 센다(D-13의 합산 규칙은 그대로, 시작 시각만 늦어진다).
- **개발 모드를 끈 뒤에도 그날 자정까지는 초기화가 유지된다 [에이전트 — 사용자에게 알렸고 이의 없음].** 자정이 지나면 0부터 센다.
- **하루 상한은 한국 시간 자정에 저절로 초기화된다**(D-13). 사용자 질문에 답한 것이고 바뀐 것 없다.
- **개발 모드가 지금 바꾸는 것:** 테스트 영상의 「영상당 1개」 예외(D-23) + [초기화] 버튼 + 칩. 하루 상한은 늘 적용한다.
- **검증:** 테스트 7개(`기능_세는구간_오늘_초기화부터_센다` 등).

## D-67 운명원은 지나가듯 자연스럽게 언급하고, 말투는 구어체로 한다 — 틀린 맞춤법·일부러 낸 오타는 쓰지 않는다 [사용자·에이전트]

- 사용자 원문: 「운명원 이라는곳을 좀 자연스럽게 언급하는게 좋을거 같은데. 여차하면 댓글 바이럴로 보이거든」. 비용은 「어차피 하이쿠로 돌리는거니까 금액은 신경쓰지 말고 해봐」. 명세 `docs/systems/draft.md`.
- **지침 `prompts/comment_system.md` [에이전트]:** 「세 박자」(D-43)의 고정 순서를 「담을 것 셋(순서 자유)」로 바꾸고, 「{brand}은 지나가듯 — 바이럴처럼 보이면 실패입니다」 절을 더했다(한 문장 곁가지 · 자리 · 부르는 말 다양화 · 어떻게 아는지 한마디 · 다른 댓글과 같은 틀 금지).
- **D-43의 「상투적 끝맺음 금지 목록」(그렇게 잘 본다던데 등)을 지웠다 [에이전트 제안 → 사용자 사후 승인]:** 에이전트가 금지 목록이 질문형 끝맺음 쏠림을 만들었다며 제안했다. 이로써 열린 결정 「상투적 끝맺음 금지 유지」는 닫혔다.
  - 경위: 에이전트가 「금액은 신경쓰지 말고 해봐」를 이 삭제의 승인으로 잘못 받아들여 먼저 지웠다. 사용자가 바로잡았다 — 「금액 신경 쓰지 말고 하라는건 초안 작성 테스트를 금액이나 시간 제약 두지 말고 자유롭게 하라는거지 맥락 바꿔가면서 하라는건 아니었어」. 이어 사후에 승인했다 — 「일단 승인 한거로 해」.
- **구어체 [사용자]:** 사용자가 「의도적으로 오타·맞춤법 틀림·마침표 안 넣기를 확률적으로」를 제안했고, 에이전트는 오타·맞춤법 오류에 반대했다(브랜드·장면 검사와 충돌, 읽는 사람에게 품질 결함, 탐지 회피로 읽힘). 사용자 결정 원문: 「1번은 구어체만(맞춤법 오류 없이)」. 지침에 「마침표 자주 생략 · 맞춤법은 바르게 · 일부러 오타 금지」를 넣었다.
- **측정(같은 영상 11개 전후, 기록장에 저장 안 함):**
  - 언급 방식: 「운명원 (에서) 연애 사주」 그대로 11→2 · 운명원을 어떻게 아는지 밝힘 8→10 · 운명원이 마지막 문장 10→8 · 규칙 통과 11/11.
  - 구어체: 마침표 21→5 · 마침표로 끝남 10→1 · 운명원이 마지막 문장 7/11.
- **비용:** 초안 작성 시험은 금액·시간 제약 없이 자유롭게 하기로 했다 [사용자 — 「하이쿠로 돌리는거니까 금액은 신경쓰지 말고 해봐」]. 규칙·지침을 바꿔도 된다는 승인이 아니다(위 끝맺음 금지 목록 항목). 재지 않았다.
- **기각 [사용자 결정, 에이전트 반대에 따름]:** 의도적 오타·맞춤법 틀림.

## D-68 테스트 영상은 목록에서 숨기지 않고, 탭 · 목록의 맨 뒤로 보낸다 [사용자]

- 사용자는 처음 「개발 모드에서만 보이게」를 원했으나, 에이전트가 반대했다: 테스트 영상은 허용 범위 안이고, 시연이 테스트 영상 게시이며 시연은 개발 모드를 끄고 찍기로 했으므로(D-23) 숨기면 시연이 불가하다. 사용자 「그럼 그냥 두자」.
- **시연을 마친 뒤 개발 모드 전용으로 바꾸는 안은 에이전트 제안일 뿐 확정이 아니다**(PROGRESS 열린 결정).
- **탭 순서 [사용자]** 「테스트 영상을 맨 오른쪽으로」: 전체 · 지정 채널 · 뜨기 직전 · 테스트 영상(D-50의 탭 순서를 고쳐 쓴다).
- **목록 순서 [사용자]** 「전체 목록에서도 테스트 영상을 맨 뒤로」: 서버 목록 = 지정 채널 영상 → 테스트 영상. 링크로 넣은 영상은 여전히 맨 앞(D-38). 테스트 `기능_서버_불러오기_테스트영상이_맨뒤이고_실패채널을_알린다`(이름을 바꿈).

## D-69 ①→②→③ 전환은 접기·펼치기 두 박자 + 단계 표시 + 기다리는 틀로 한다. 초안 받는 동안 [댓글 달기]는 꺼진다 [사용자·에이전트]

- 사용자 원문: 「1 -> 2로 넘어갈때 화면 구성이 갑자기 크게 바뀌어서 혼동이 와」. 명세 `docs/systems/dashboard.md`.

  - 지금 칸이 위로 접히고(0.38초) 새 칸이 펼쳐진다. 위에 붙어 따라오는 단계 표시(① ② ③). ① 띠에 「영상 목록은 여기 접혀 있어요」 + 반짝임.
  - 브라우저가 그림을 멈추면 0.68초 뒤 끝 모습으로 건너뛴다. 숨긴 탭 · 동작 줄이기 설정이면 즉시 전환.

## D-72 「지어낸 후기」 검사는 브랜드 곁의 직접 겪은 표현을 보고, 남의 경험을 전해 들은 말은 통과시킨다 [사용자·에이전트]

- 사용자 원문: 「후기 검사만 좀 하자」. 앞서 에이전트가 선택지 셋 중 「2번 운명원 곁 경험 표현 패턴 검사」를 추천했고 그 방식으로 진행했다. D-55에서 열어 두었던 결정을 닫는다. 명세 `docs/systems/guard.md`.
- **방식 [에이전트]** (`agent/guard.py`): 브랜드가 나온 자리마다 뒤 30글자에서 직접 겪은 표현(가봤 · 갔었 · 갔을 · 가서 · 다녀 · 들렀 · 방문 · 예약했 · 상담 받 · 봐 줬 · 해 준(해 준다 제외) · 말씀하신 · 봤는데 · 받았 · 맞더라 · 소름 · 덕분에 · 단골 · 「에서 들은」 등)을, 앞 12글자에서 꾸미는 말(다녀온 · 갔던 · 가 본 …)을 찾는다. 「추천 받았」 · 「검색해 봤는데」는 제외. 표현 묶음은 코드 상수다(링크·해시태그 꼴과 같은 취급).
- **남의 경험을 전해 들은 말은 통과 [에이전트]:** `_heard_from_others` — 앞 25글자 안에 남을 가리키는 주어 + 뒤의 전해 들은 끝맺음, 또는 「다녀온 지인이」처럼 남을 꾸미는 꼴. 남과 함께한 내 경험(「친구랑 같이 다녀왔는데」)은 계속 막고 테스트로 고정했다.
- **설정의 `forbidden_phrases`에도 같은 예외를 적용한다 [사용자]** — 원문 「설정의 금지 표현 목록에도 남의 경험을 전해 들은 말은 통과시키는 예외를 적용해 줘」. 같은 판단 함수를 쓴다(로직 파편화 방지). 옵션 페이지 「금지 표현」 설명도 고쳤다.
- **측정:** 규칙을 보지 않은 에이전트가 쓴 예문(지어낸 후기 30 · 정상 30)에서 처음 22/30(73%)을 잡았다. 그 예문을 보고 다듬은 뒤 30/30(블라인드가 아니라 과대평가) · 정상 오탐 8→0 · 실제 초안 61개 오탐 0.
- **한계:** 규칙을 만든 쪽이 본 예문으로 잰 30/30은 과대평가다. 블라인드 값은 22/30이다.

## D-73 README는 간결한 사용자용으로 쓰고, 제작 의도는 README 안의 절로 둔다 [사용자]

- 사용자 원문: 「readme를 좀 더 간결하게 써보자. 사용 방법, 키 설정, 같은것들 위주로. 폴더 구조 같은건 필요 없어. 기술적인 얘기는 가급적이면 빼놓고」. 처음엔 폴더 구조 · 개발자용 · 기술 설명까지 길게 썼다가 이 지시로 줄였다.
- **순서:** 준비물 → 키 설정(실행 전에, `.env.example`을 복사해 `.env`로) → 실행 → 유튜브 계정 연결 → 사용 방법 → 알아 둘 규칙 → 설정 바꾸기 → 제작 의도 → 쓴 오픈소스(이름 · 라이선스 표).
  - 키 설정을 실행 앞에 둔 것은 사용자 원문 「실행 하기 전에 키 설정이 제대로 되어 있는지 확인 하라고 해야겠네」에 따랐다.
  - 실행기는 이미 있는 `.env`를 덮어쓰지 않는다(코드 확인 [에이전트]).
  - 라이선스는 설치된 패키지 정보로 확인했다. 글꼴의 SIL OFL 1.1은 확인하지 못했다.
- **제작 의도 [사용자]:** 에이전트가 쓴 두 판(형식적인 글 → 「AI 냄새가 진동」 → 1인칭으로 다시)을 사용자가 「그냥 내가 읊을테니까 너가 한번 정리해서 써보는게 좋을거 같은데」로 바꿔, 사용자가 직접 말한 내용을 정리해 썼다.
  - 핵심: 사용 편의성 · 최소 절차(bat 하나로 실행) · 대시보드에서 거의 모든 것을 제어(API 키 · 개발 모드 · AI 모델 설정만 대시보드 밖).
  - 「이정도 제작 의도면 README에 포함 시켜도 되겠는데」로 README 안 「제작 의도」 절이 되었고, 따로 만들었던 제작 의도 파일은 사용자 지시로 지웠다. 제작 의도는 README 안에만 있다.
- **기각 [사용자]:** 「하네스 구조」 문단 — 사용자가 직접 지웠다(「읽어보니 하네스는 아무래도 빼는게 좋을거 같아서」). 에이전트가 쓴 앞의 두 판.
